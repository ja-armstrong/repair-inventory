# 08: Labels and scan-to-receive

**What to build:** The physical half of the PO: printing and receiving. For each PO line, the system pre-assigns expected serials (system-assigned, unique). A print view renders one Code 128 label per expected part — serial barcode plus SKU and part name, CSS-sized to the label stock (current 2-5/16" × 4", parameterized for the future 2" × 1") — printable via the browser on the Dymo. Receiving is scan-driven: scanning (typing) a serial on the receive screen adds that part to inventory as Available, marks the line's received quantity up, computes Partially received vs Received automatically, refreshes the SKU price with the received unit cost, and auto-reserves the part to the batch whose outstanding demand it fulfills. A PO can be closed with a shortfall via required note.

**Blocked by:** 05 (parts on batches), 07 (purchase orders create and approve).

## Comments

- **Endpoints** (all under `/api/purchase-orders`, session-gated):
  - `GET /:id/labels` — one entry per expected serial (serial, skuId, skuName, lineId, received) plus the configured label size; 409 while Awaiting approval.
  - `POST /:id/receive` `{ serial }` — creates the part as Available (or auto-reserves), bumps the line, refreshes price, recomputes status; returns `{ partId, serial, reserved, demandId, batchId, deviceId, priceChanged, status, purchaseOrder }`. Rejections: 400 unknown serial, 409 already-received / wrong PO / bad PO status — serial-identity messages deliberately take precedence over the status guard (a duplicate scan deserves "already received", not "wrong status").
  - `POST /:id/receive-consumable` `{ lineId, quantity }` — consumable lines have no serials; this is how they reach Received.
  - `POST /:id/close` `{ note }` — close-with-shortfall from In-transit / Partially received only; 409 when fully received (nothing to close) or already closed.
- **Serial pre-allocation design:** expected serials are assigned when a manager approves the PO (plus an idempotent fallback on the labels view for POs approved before this shipped — evented, never silent). The parts domain gained an additive allocator, `server/domains/parts/serials.ts`: `nextPartId` is now max over `serialized_parts` ∪ `serial_id_claims` + 1, so PO pre-assignment claims ids (`serial_id_claims`, migration 0009) and ad-hoc intake can never hand out the same barcode. On receipt the part row is inserted with the claimed id/serial and the claim is deleted — the barcode is stable from print through receive. Consumable PO lines get no serials (cost-only per CONTEXT.md). Side effect: abandoned POs leave permanent gaps in the P##### sequence.
- **Label parameterization:** settings keys `label_width_sixteenths` / `label_height_sixteenths` (seeded 37/64 = 2-5/16" × 4"; the 2" × 1" target stock is 32/16), manager-editable via the existing `PATCH /api/settings`. Sixteenths of an inch because Dymo stock is fractional and the settings contract is whole numbers. `GET /:id/labels` returns computed inches; the print view sizes labels via CSS variables and `@media print` hides app chrome, one label per page.
- **Auto-reserve flow:** on each receipt the part fulfills the highest-priority open demand for the SKU — the line's own demand first, then any demand this PO marked ordered (`purchase_order_demand` link), then the oldest open demand. The demand flips to fulfilled (`fulfilled_at/by`, `demand.fulfilled` event, careful guarded direct UPDATE on demand_records — batchparts exports no fulfillment write path; noted per parallel-safety rules). When the demand has a device (and it is not terminal), the part is reserved via batchparts' own guarded `reservePart` + `insertAttachment` at the PO line's unit cost, with `part.reserved` / `device.part_reserved` events mirroring ticket 05's shape. A demand without a device is fulfilled with the part left Available — recorded in the events, never guessed. Device status stays "Parts needed"; leaving it is a human call (ticket 05 rule, untouched).
- **Status machine:** Partially received / Received are computed from line received quantities inside the receive transaction and written with an auto `po.status_changed` event; close-with-shortfall is the only other status write after In-transit. Shortfall is visible per line (`shortfall`) and in total (`shortfallTotal`) on PO detail.
- **Price refresh:** every receipt sets the SKU price to the line's unit cost and bumps `price_updated_at` (staleness reset), recording `sku.price_changed` with `reason: "po_receive"` even when the amount is unchanged — the receipt confirms the price; nothing writes silently.
- **Migration:** `0009-po-receiving.sql` (the next free number when this work started; the briefing's "0010" anticipated a different ordering — gapless numbering wins). Tables: `serial_id_claims`, `purchase_order_expected_serials` (CHECK: part received ⟺ part_id+received_at+received_by all set), `received_quantity` on lines, close columns on POs.
- **Cross-domain touches (all additive):** `parts/serials.ts` new allocator + `parts/index.ts` now imports it (single source of truth for the serial scheme); `parts/settings.ts` two new setting definitions; `parts.test.ts` settings-shape assertion updated to include them.
